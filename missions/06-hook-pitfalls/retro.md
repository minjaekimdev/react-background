## 돌아보기

### 1번 — "시점" 분리 vs "무엇을 위해" 분리

**이해하기 쉬운 쪽:** 보통 `useEffect`("무엇을 위해") 분리입니다.  
이유는 **응집도** 때문입니다. 같은 관심사의 코드가 한 곳에 모여 있으니까요.

- **클래스 시대:** 타이머 하나를 쓰려면 `componentDidMount`(등록)와 `componentWillUnmount`(해제) 두 곳에 코드를 흩어 써야 했고, 수백 줄이 떨어져 있었습니다. 거꾸로 mount 시점에는 타이머+구독+로깅처럼 서로 다른 관심사가 한 메서드에 뭉치고, update 시점에도 비슷한 코드를 복붙해야 했습니다. 미션 6의 스톱워치가 클래스였다면 `componentDidMount`에 `setInterval`, `componentWillUnmount`에 `clearInterval`이 따로 있었을 겁니다.
- **`useEffect`:** "타이머"라는 관심사 하나가 등록 + `return () => clearInterval(id)`(정리)로 인접하게 모입니다. 정리 함수를 잊기 어렵고, STEP 4에서 봤듯 `StrictMode`가 cleanup 누락을 개발 중에 바로 드러내 줍니다.

**실수하기 쉬운 쪽:** 둘 다 쉽지만, 실수의 **"종류"**가 다릅니다.

| 구분 | 실수의 종류 | 드러나는 방식 |
| :--- | :--- | :--- |
| **클래스** | `componentWillUnmount`에 해제 깜빡(메모리 누수), mount/update 로직 중복 복붙, update에서 조건 빠뜨려 무한 `setState` | **암묵적** — 조용히 숨어 프로덕션까지 감 |
| **`useEffect`** | 의존성 배열 — 빈 배열의 stale closure(= STEP 1 버그), 빠뜨림, 과다 주입으로 무한 재실행 | **명시적** — 배열이라는 계약이 코드에 보임 |

> **핵심:** `useEffect`는 실수 자리가 명시적입니다. 의존성 배열이라는 "계약서"가 눈에 보이니, 실수해도 그 자리를 지적받으며 배웁니다. 클래스는 시점이라는 암묵적 규칙에 실수가 숨죠. **명시적 실수는 학습 비용이지만, 암묵적 실수는 버그 비용입니다.** 다만 그 대가로 의존성 배열이라는 새로운 개념을 배워야 했고, STEP 1에서 그 학습 비용을 직접 냈습니다.

### 2번 — 편리와 함정이 같은 자리에서 나오는 다른 예

#### 예시 ① Python의 가변 기본 인수

`[]` 버그와 구조가 똑같은 대표 사례입니다.

```python
def add_item(item, items=[]):   # 편리: 인수 생략 가능
    items.append(item)
    return items

add_item(1)  # [1]
add_item(2)  # [1, 2] ← 새 호출인데 옛 리스트에 쌓임!
```

기본 리스트는 함수 정의 시 딱 한 번 만들어져 모든 호출이 공유합니다. "기본값을 안 써도 되는 편리"와 "호출 간에 상태가 오염되는 함정"이 정확히 같은 자리(기본 인수)에서 나옵니다. `useEffect(fn, [])`의 "마운트 때 한 번 등록되어 공유됨"과 동형입니다.

#### 예시 ② Angular.js의 양방향 바인딩

미션 3 회고에서 이미 비교한 주제죠.

- **편리:** `ng-model` 한 줄이면 입력↔모델이 자동 동기화. 상태 설계·끌어올리기 고민 필요 없음.
- **함정:** 값이 "사용자가 입력한 것인지, watcher가 써 넣은 것인지" 추적 불가, watcher 핑퐁·순환 발생.

자동 동기화라는 마법이 편리의 원천이자 함정의 원천입니다. `[]`가 "React가 마운트 시점을 대신 추론해 주는 것"이라면, 양방향 바인딩은 그 마법의 극단판입니다.

#### 예시 ③ `innerHTML` 한 줄 렌더 (미션 1)

- **편리:** 문자열 한 줄로 화면을 통째로 다시 그림.
- **함정:** 매번 전체 파싱 비용 + 이스케이프를 빼먹으면 XSS. 미션 1의 `renderList()`에서 이스케이프 코드를 직접 봤습니다.

> **메타 교훈:** 함정은 "편리를 만들려고 라이브러리가 대신 추론해 준 것"이 사용자 의도와 어긋날 때 생깁니다. 그래서 성숙한 API는 편리를 없애는 게 아니라 암묵적 추론을 명시적 계약으로 바꿉니다 — 의존성 배열이 바로 그 계약이에요. 그리고 편리는 계약을 비우는 방식(`[]`)으로 돌아오고, 함정도 그 자리에 함께 남죠.
>
> **라이브러리를 평가할 때 물어볼 질문:** "이 편리가 만드는 함정은, 실수로 즉시 드러나는가(에러/경고), 아니면 조용히 숨는가?"

### 3번 — "`useEffect`를 쓰기 전에 물어볼 질문은?" (한 문장)

> **"이 값(또는 이 작업), 이미 가진 상태만으로 계산(또는 처리)할 수 없나요?"**

- **계산 가능한 파생값이면:** 상태도 만들지 말고 effect도 쓰지 않고, 렌더 중에 계산합니다. 미션 2의 원칙("계산 가능한 값은 상태로 만들지 않는다")이 이펙트에도 그대로 적용되는 거예요. `SearchList`가 증명했죠 — `filtered`는 `query`만 있으면 계산되니, effect를 지우자 렌더가 정확히 1회가 되고 뒤처짐 위험도 구조적으로 사라졌습니다.
- **그 질문을 통과했다면(진짜 effect가 필요했다면) 다음 질문:** "이건 외부 시스템(타이머·구독·서버)과의 동기화인가, 아니면 이벤트 핸들러로 충분한가?" — 타이핑에 반응하는 UI 로직은 이벤트 핸들러에, 외부 동기화만 effect에 둡니다. 이 체크리스트 전체가 공식 문서 *You Might Not Need an Effect*의 내용입니다.
