# 미션 1 · DOM 지옥에서 살아남기 (바닐라 JS)

> **"React가 왜 만들어졌는지"는, React 없이 앱을 한 번 만들어 보면 가장 빨리 이해됩니다.**

## 이 미션의 배경 이야기

2011년, 페이스북 광고팀은 점점 커지는 웹 앱에서 큰 고통을 겪고 있었습니다.
React를 만든 Pete Hunt의 회고(ACM Queue 인터뷰)에는 이렇게 나옵니다:

> "가장 큰 문제는 **UI를 비즈니스 로직과 애플리케이션 상태와 동기화된 상태로 유지하는 것**이었다.
> 예전 방식에서는 이벤트 리스너를 등록하고, 데이터가 바뀌면 어떤 DOM을 고쳐야 하는지 사람이 직접 찾아 수정했다."

데이터가 한 곳에서 바뀌면 → 그 데이터를 참조하는 **모든 화면 조각(뱃지, 목록, 요약, 버튼 상태…)을 개발자가 전부 찾아서 갱신**해야 했습니다. 하나라도 빼먹으면 화면과 데이터가 어긋나는 버그가 생깁니다. 페이스북은 이 문제를 풀기 위해 내부 프레임워크 Bolt → **FaxJS(2011, Jordan Walke의 사이드 프로젝트)** → **React(2013)**로 발전시킵니다.

이 미션에서 여러분이 겪을 고통이 바로 그것입니다.

## 준비물

- HTML/CSS/JS 기초 (DOM 선택, addEventListener)
- 선행 미션: 없음 (여기가 시작입니다)

## 실행 방법

```bash
npm install   # 저장소 루트에서 딱 한 번
npm run dev   # 개발 서버 실행
```

브라우저에서 `http://localhost:5173/missions/01-dom-hell/` 을 열거나, 루트 미션 허브에서 클릭하세요.
`app.js`를 수정하면 새로고침만으로 결과를 볼 수 있습니다.

## 미션 목표

`app.js`의 TODO를 따라 **할 일 앱**을 완성하면서, 아래를 몸으로 느끼는 것:

1. 데이터를 바꾸면 → **어떤 화면 조각을 갱신할지 개발자가 전부 기억해야** 한다.
2. 데이터를 바꾸는 경로(입버튼, 빠른 추가, 체크, 삭제…)가 늘어날수록 **갱신 코드가 복붙으로 늘어난다**.
3. 갱신 하나를 빼먹으면 → **데이터와 화면이 어긋나는 버그**가 생긴다.

## STEP 0 · 일단 문제 상태를 관찰하기 (구현 전)

`npm run dev`로 페이지를 열어 보세요. 리스트에는 할 일이 2개 보이는데, 뱃지와 요약 패널은 **0**입니다.
코드에서 `renderList()`만 호출하고 통계 갱신은 아직 안 했기 때문입니다.
**지금부터 끝까지, "데이터와 화면이 어긋난 상태"가 이 미션의 주인공입니다.**

## STEP 1 · 추가 기능과 "갱신 목록"의 탄생

- `renderStats()` 함수를 구현하세요 (뱃지, 전체/완료/남음, 격려 메시지, 진행률 바).
- 폼 submit 핸들러의 TODO를 완성하세요.
- 새 할 일을 추가하면 **리스트, 뱃지, 요약, 진행률**이 전부 바뀌어야 합니다.

✅ 체크리스트: 이 한 번의 "추가"로 내가 손대야 하는 화면 조각은 **몇 개**였나요? README 마지막의 기록 칸에 적어 두세요.

## STEP 2 · 토글/삭제 — 또, 또, 갱신 호출

- 목록의 체크박스(완료 토글)와 삭제 버튼을 이벤트 위임으로 구현하세요.
  - `li.dataset.id`는 **문자열**입니다. `Number()`로 바꿔야 비교할 수 있습니다.
- 구현할 때마다 `renderList()`, `renderStats()` 호출을 잊지 않으셨나요?

## STEP 3 · (중요) 의도적으로 버그를 만들어 보기

빠른 추가 버튼의 TODO를 완성하되, **일부러 `renderStats()` 호출을 빼고** 실행해 보세요.

- "💧 물 마시기"를 클릭 → 목록에는 생겼는데 **뱃지는 그대로**입니다.
- 이것이 2011~2012년 페이스북 엔지니어들이 매주 만나던 버그입니다.
  데이터는 한 곳에서 바뀌었는데, 그 데이터를 보는 화면이 여러 곳이라 **한 곳이라도 갱신 호출을 빼먹으면** 어긋납니다.
- 확인했으면 `renderStats()`를 넣어 고치세요. 그리고 느껴 보세요 — **"고치는 방법"이 아니라 "이 실수가 계속 재발할 구조"가 문제**라는 점을.

## STEP 4 · 완료 항목 삭제 — 네 번째 진입 경로

- `#clear-done` 버튼으로 done인 항목을 일괄 삭제하고 갱신하세요.
- 진입 경로가 4개가 되었습니다. 새 경로가 생길 때마다 무엇을 복붙했나요?

## STEP 5 · 리팩토링 — 그래도 남는 것

- 갱신 코드를 `refresh()` 함수 하나로 모아 보세요 (`solution/app.js` 참고).
- 확실히 낫습니다. 그런데 새 화면 조각(예: "오늘 완료 시간" 표시)을 하나 추가하면?
  → **refresh() 안에 또 한 줄을 사람이 추가해야 합니다.** 컴파일러도, 프레임워크도 잊었다고 알려주지 않습니다.
- Pete Hunt가 말한 "찾아내기 어려운, 아무도 해결 못 하던 버그들(nobody could solve)"이 바로 여기서 나옵니다.

## 돌아보기 (미션 2로 가기 전)

1. "데이터가 바뀔 때 화면을 갱신한다"는 책임이 지금 코드에서 **누구**의 몫인가요? (개발자? 라이브러리?)
2. 진입 경로가 100개면 이 코드는 어떻게 될까요?
3. 반대로 "데이터가 무엇이든 **화면 전체를 데이터로 다시 그린다**"면 위 문제들이 어떻게 사라질까요? — 이것이 다음 미션의 주제이자 React의 핵심 발상입니다. (*"데이터가 바뀔 때마다 뷰를 통째로 다시 그릴 수 있다면 훨씬 단순할 텐데"* — React 공개 발표에서 Tom Occhino가 처음 던진 질문입니다.)
