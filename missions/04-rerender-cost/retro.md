## 돌아보기
### 1. React의 "전체 재렌더"는 바닐라 ①에 가까운가요, ②에 가까운가요? virtual DOM diff가 해주는 것은 무엇이고, 못 해주는 것은 무엇인가요?
#### 내 답안
React의 "전체 제렌더"는 바닐라 1에 가깝다. virtual DOM diff는 이전과 비교해서 변경된 부분만 실제 DOM에 반영하는 것까지는 해주지만, 렌더 페이즈에서의 함수 컴포넌트 실행 자체를 막아주지는 못한다. 
  
#### 모범 답안
- "실행" 관점에서는 바닐라 ①에 가깝다. 버튼을 누르면 바뀌지 않은 9,999개 행의 함수까지 전부 다시 실행됩니다. 측정 패널의 "실행된 행 수 10,000"이 그 증거입니다.
- "실제 DOM 반영" 관점에서는 바닐라 ②에 가깝다. diff 덕분에 실제 DOM에서 만지는 곳은 1곳뿐입니다. 나머지 9,999개 노드는 화면에 그대로 재사용됩니다.
  
virtual DOM diff가 해주는 것: 예전 설계도(가상 DOM)와 새 설계도를 비교해서, 실제 DOM에는 달라진 최소한의 부분만 반영하는 것. 즉 "DOM 조작 비용"은 diff가 줄여줍니다.

diff가 못 해주는 것: 컴포넌트 함수를 다시 실행하는 비용을 줄이는 것. diff는 함수를 전부 실행해 나온 결과를 "실행 후에" 비교하는 도구이기 때문에, "무엇이 바뀌는지"를 미리 알고 실행을 건너뛰는 일(= memo의 역할)은 못 해줍니다.
  
### 2. memo를 "무조건 다 붙이면 되는 것"이 아닌 이유는?
#### 내 답안
memo는 props 비교 비용, 측정 비용이 존재한다. 따라서 성능이 저하되는 꼭 필요한 곳에만 적용해야 한다.

#### 모범 답안
1. memo 자체에도 비용이 든다. memo는 렌더 때마다 이전 props와 새 props를 하나하나 비교(얕은 비교)합니다. 이 비교 비용이 매 렌더마다 추가되는데, 재렌더가 드문 컴포넌트에 붙이면 비교 비용만 나가고 이득은 없습니다.
2. 불변성 규칙이라는 새로운 계약이 생긴다. memo가 작동하려면 "바뀌지 않은 데이터는 같은 참조를 유지"해야 합니다. 이 규칙이 깨지면 두 가지 사고가 납니다 — 매번 새 객체를 만들어 넘기면 memo가 조용히 무용지물이 되고, 반대로 기존 객체를 직접 고치면 참조가 같아서 바뀌었는데도 화면이 안 그려지는 정확성 버그가 됩니다.
3. 프리마처 오버엔지니어링. React 공식 문서(memo)도 경고하는 부분으로, 대부분의 컴포넌트는 재실행이 워낙 빨라서 memo 없이도 충분히 빠릅니다. 성능 문제를 측정하기도 전에 미리 다 붙이는 것은 코드만 복잡하게 만드는 일입니다. 이 미션에서 10,000행이라는 극단적인 상황을 굳이 만든 이유가 "memo는 이렇게 큰 비용이 실측될 때 쓰는 도구다"를 체감시키기 위해서입니다.


#### 3. 미션 1에서 "갱신 호출 목록을 개발자가 관리"했던 고통과, 이번 미션에서 "memo/불변성 규칙을 개발자가 관리"하는 부담 — 이 둘은 같은 종류의 일인가요?
같은 종류의 일이 아니다. 갱신 호출 목록을 개발자가 관리하는 고통은 모델과 뷰의 불일치로 인한 고통이라면, memo/불변성 규칙을 개발자가 관리하는 부담은 렌더링 성능 관점에서의 부담이다.

## 회고
- 리액트는 모델과 뷰의 동기화를 위해 컴포넌트 전체 실행을 한다. 따라서 불필요한 실행을 막기 위해 memoization이 필요하다. 하지만 memoization 또한 props 비교와 같은 비용이 존재하기 때문에, 성능 저하가 발생하고 props가 이전과 같다는 것이 확정적인 부분에만 선택적으로 적용해야 한다.
