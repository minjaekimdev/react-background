- 양방향 바인딩 방식은 어떤 값이 언제 바뀌는지 추적하기 어렵다.

```js
$scope.$watch('quantity', calcSubtotal);        // 수량 → 소계
$scope.$watch('price',    calcSubtotal);        // 단가 → 소계
$scope.$watch('coupon',   applyDiscount);       // 쿠폰 → 소계를 또 고침
$scope.$watch('subtotal', calcTax);             // 소계 → 세금
$scope.$watch('subtotal', calcShipping);        // 소계 → 배송비
$scope.$watch('tax',      calcGrandTotal);      // 세금 → 총액
$scope.$watch('shipping', calcGrandTotal);      // 배송비 → 총액
```

총액은 세금에서, 세금은 소계에서, 소계는 수량/단가/쿠폰 세 곳에서, 즉 값이 바뀌는 입구가 그래프의 모든 노드라서 원인을 찾으려면 watcher 그래프 전체를 머리로 실행해봐야 한다. 심지어 watcher 실행 순서도 결과에 영향을 주고, 서로를 건드리면 순환까지 가능해진다.

### step1 트레이싱 표
| 값 | 상태로 저장해야 하는가? | 이유 |
| --- | --- | --- |
| 마지막에 입력한 숫자 | O | 해당 값을 통해 다른 온도를 계산해야 하기 때문이다. |
| 그 숫자의 단위(c 또는 f) | O | 위와 동일 |
| 반대 단위로 환산한 숫자 | X | 상태로 관리할 필요없이 파생값으로 계산된다. |
| "끓는지" 여부 | X | 상태로 관리할 필요 없이 파생값으로 계산된다.|

### 돌아보기
#### 1. 이전에는 두 입력이 "서로를 모르는" 컴포넌트였습니다. 지금은 무엇 덕분에 동기화되나요? (단일 출처(single source of truth))
- 부모의 상태 덕분에 동기화된다.
- 모범 답안: 두 입력의 각자의 상태를 기억하지 않고, (temperature, scale)이라는 단일 출처를 App 혼자 기억하기 때문이다. 두 입력창에 보이는 같은 값은 전부 이 원본에서 계산된 파생값이라서, 원본이 바뀌면 두 화면이 항상 함께 갱신된다.

#### 2. 데이터가 부모 → 자식으로만 흐른다면, 두 입력 컴포넌트는 서로를 전혀 호출하지 않습니다. 왜 그래도 동기화될까요?
- 부모의 상태 덕분에 동기화된다.
- 모범 답안: 동기화가 컴포넌트 간 직접 통신으로 일어나는 게 아니기 때문이다. 흐름은 항상 이렇다.
```
1. 사용자 입력 → 자식이 onChange로 부모에게 변경을 통지 (위로 올라가는 건 "사실"이 아닌 "요청")
2. 부모가 setTemperature/setScale로 원본을 갱신
3. React가 App을 재렌더 → 파생값을 다시 계산
4. 새 props가 두 입력에게 모두 내려감 (위→아래)
```

즉 두 입력은 서로를 모른 채, 각자 부모와만 대화한다. 원본이 갱신되면 전체가 다시 그려지는 구조라, A 입력의 변경이 B 입력에 전달되는 게 아니라 B도 원본에서 다시 계산될 뿐이다. 데이터는 아래로만 흐르고, 위로는 변경 요청만 흐르는 단방향 흐름이 동기화를 만든다.


#### 3. 이 구조라면 새로운 표시(예: 켈빈 입력)를 추가할 때 무엇만 하면 되나요? 갱신 누락 위험은?
- 새로운 표시를 추가할 때 부모 컴포넌트(App)에 파생값 계산 로직을 추가해주기만 하면 된다. 바닐라 JS에 비해 갱신 누락 위험이 현저히 줄어든다.
- 모범 답안: 할 일은 세 가지 뿐이다.

```
1. 환산 함수 추가: function toKelvin(c) { return c + 273.15; }
2. 파생값 계산 한 줄: const kelvin = scale === 'k' ? temperature : tryConvert(temperature, toKelvin);
3. `<TemperatureInput label="켈빈 (K)" value={kelvin} onChange={(v) => { setScale('k'); setTemperature(v); }} />` 렌더에 추가
```
기존 섭씨/화씨/판정 컴포넌트는 한 글자도 고치지 않습니다. 수정이 아니라 순수 추가만으로 확장돼요.

갱신 누락 위험은 없습니다. 켈빈 값은 상태가 아니라 원본의 계산값이라, 원본이 바뀔 때마다 렌더에서 항상 다시 계산됩니다. "켈빈 표시를 갱신하는 호출"이라는 대상이 애초에 존재하지 않으니 빼먹을 수 없어요. 반면 바닐라였다면 켈빈 input을 갱신하는 코드를 모든 변경 경로에 복사해 넣어야 하고, 한 곳이라도 빼먹으면 켈빈만 옛 값으로 멈추는 미션 1식 버그가 생깁니다.


#### 4. 양방향 바인딩(Angular.js 스타일)이었다면 이 예제는 어떻게 짜였을까요? 편의성은? 추적 가능성은?
- 어떤 값이 수정되어 무엇을 바꾸었는지 추적하기 어려웠을 것이다.

ng-model="celsius", ng-model="fahrenheit"로 두 입력을 각자 모델에 묶고, watcher 두 개로 서로를 환산해 쓰는 구조가 됩니다:

```js
$scope.$watch('celsius',     (v) => { $scope.fahrenheit = toF(v); });
$scope.$watch('fahrenheit',  (v) => { $scope.celsius    = toC(v); });
```
편의성: 더 높습니다. 상태 설계·끌어올리기·onChange 통지를 고민할 필요 없이 필드를 모델에 바인딩만 하면 되니까, 모델이 작은 이 예제 수준에서는 React 방식보다 코드가 짧을 수 있어요.

추적 가능성: 나쁩니다. celsius 모델에 37.78이 들어 있다면 그것이 사용자의 직접 입력인지, fahrenheit watcher가 환산해 쓴 값인지 코드만 봐선 알 수 없어요. 두 watcher가 서로를 자극하는 환산 핑퐁이 생기고("마지막에 편집한 쪽은 갱신 금지" 같은 묵시적 규칙에 의존하게 됨), 값이 바뀌는 입구가 여러 개라 디버깅하려면 watcher 그래프 전체를 머리로 실행해야 합니다.

반면 React 방식은 값의 입구가 handleCelsiusChange/handleFahrenheitChange 두 함수로 모여 있어서 "이 온도는 언제, 어디서 바뀌는가"를 grep으로 추적할 수 있습니다. 편의성 ↔ 추적 가능성의 트레이드오프를 보여주는 최소 예제가 이 앱인 셈이죠.
