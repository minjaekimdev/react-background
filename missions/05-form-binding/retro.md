## 비교 기록 칸

| 관점                                   | 네이티브 ①           | React 제어 ②                            |
| -------------------------------------- | -------------------- | --------------------------------------- |
| 값의 원본                              | DOM                  | state                                   |
| 이메일 input을 위한 코드               | 1줄 (HTML)           | useState 1줄 + value 1줄 + onChange 1줄 |
| 타이핑 1글자당 App(또는 페이지) 재실행 | 0회                  | 1회(StrictMode 2회)                     |
| 값 전체를 읽는 방법                    | `new FormData(form)` | state 그대로                            |
| 실시간 표시 만들 때 갱신 누락 가능?    | 있음                 | 없음                                    |

## 돌아보기

### 1. React는 왜 "input의 값을 DOM에 맡겨 두는 것"을 기본값으로 안 만들었을까요?

#### 모범 답안

답: 값이 DOM에만 있으면 React의 핵심 공식 — "UI는 state의 함수" — 가 성립하지 않기 때문. 힌트의 세 가지로 확인해 봅니다.

(a) 렌더로 다시 그릴 때 값이 유지되는가? → 보장할 수 없다.
React의 렌더 모델은 "state로부터 화면 설계도를 새로 만든다"입니다. 값이 state에 없으면, React는 그 값의 존재조차 모르고 재렌더 과정에서 그 노드를 갈아엎을 수도 있습니다. 조건부 렌더링, 리스트 순서 변경, key 변경 같은 구조 변화가 일어나면 DOM 노드가 새로 만들어지고, DOM에만 있던 값은 증발합니다. 지금 폼에서 타이핑이 유지되어 보이는 건 단순한 경우엔 같은 노드를 재사용하기 때문이고, 그건 보장이 아니라 우연에 가깝습니다.

(b) 다른 UI(버튼 활성화, 미리보기)에서 쓸 수 있는가? → 못 쓴다.
"이메일이 유효하면 제출 버튼 활성화"를 만들고 싶어도, 값이 DOM에만 있으면 React는 값이 바뀐 걸 알 방법이 없어서 재렌더 자체가 일어나지 않습니다. 버튼은 영원히 옛 모양으로 남겠죠. 이걸 해결하려면 결국 이벤트 리스너에서 수동으로 갱신 코드를 짜야 하는데, 그럼 미션 1의 뱃지 버그(갱신 누락) 구조가 그대로 돌아옵니다.

(c) 값의 현재 상태를 코드로 알 수 있는가? → 선언적으로는 알 수 없다.
DOM에만 있는 값은 노드 안에 숨겨져 있어서, 필요할 때마다 직접 찾아 읽어야(ref, FormData) 합니다. 로그로 찍거나, 조건문에 쓰거나, 다른 컴포넌트에 props로 전달할 수 없습니다. 값이 데이터 모델(state) 밖에 있으니 렌더 함수 눈에 보이지 않는 거예요.

한 줄 정리: 값의 원본이 state여야 "state만 바꾸면 화면 전체가 따라온다"는 예측 가능성이 성립합니다. 그 대가가 input 하나당 useState + value + onChange의 세리머니입니다

### 2. STEP 1(비제어)이 "나쁜 것"은 아닙니다. 언제 비제어가 합리적인가요?

#### 내 답안

하위나 다른 컴포넌트에서 value가 사용되지 않거나, 폼 제출의 기능만 하는 경우

#### 모범 답안

답: "타이핑 도중에 UI가 이 값에 반응할 필요가 없는가?"가 예이면 비제어가 합리적입니다.

- 제출 시에만 값이 필요한 폼. 회원가입, 검색창처럼 입력 중엔 아무 UI가 반응할 필요 없고 제출 순간에만 읽으면 되는 폼. 타이핑 내내 재렌더되는 비용(렌더 횟수 글자당 +1)을 안 치러도 됩니다.
- React가 아예 다루지 못하는 input. 대표적으로 <input type="file"> — 값이 파일이라 state 문자열로 관리되지 않으므로, 공식 문서도 비제어로만 다루라고 명시합니다.
- 렌더 비용이 큰 대형 폼. 글자 하나마다 무거운 컴포넌트 전체가 다시 실행되는 상황(미션 4에서 배운 비용)이라면, 값에 관여하지 않는 비제어 쪽이 유리합니다.
- 네티브 동작·외부 라이브러리에 맡기고 싶을 때. 브라우저 기본 기능(미션 5-①의 maxlength, required 등)을 최대한 활용하고 싶은 경우.
  방법은 useRef로 input을 가리켰다가 제출 시점에 ref.current.value로 읽거나, 초기값만 필요하면 defaultValue를 쓰는 것입니다. 공식 문서(Escape Hatches)도 이를 "탈출구"로 소개할 정도로 정당한 선택지예요.
  한 줄 정리: 기본값은 제어, 하지만 값이 "렌더에 관여할 필요가 없다면" 비제어가 더 싸고 더 단순합니다.

### 3. 양방향 바인딩은 "편의"를 얻고 "추적 가능성"을 잃었습니다. React는 그 반대입니다. 당신이 팀 리더라면 어떤 트레이드오프를 택하겠나요? 이유는?

답 (예시): 규모가 있고 사람이 많은 팀이라면 React 쪽 — "명시적인 한 방향 흐름"을 택합니다.
이유:

1. 디버깅 비용이 타이핑 비용보다 크다. "이 화면 값이 대체 어디서 왔지?"를 추적 못 하는 것(양방향 바인딩의 폐해)은 버그 하나당 몇 시간씩 먹고, value/onChange 세리머니는 글자 몇 개짜리 비용입니다. 미션 5-②에서 렌더 횟수가 글자당 1씩 늘어난 것도, 대가가 눈에 보이는 형태라는 뜻이지 잘못된 것이 아닙니다.
2. 일관성이 온보딩 비용을 줄인다. 자동 마법(암묵적 동기화)은 편하지만, 팀원마다 "마법이 어디서 도는지"를 따로 이해해야 합니다. 값의 원본이 state 하나로 모이는 규칙은 새로 온 사람도 한 문장으로 설명할 수 있어요.
3. 단, 하이브리드 규칙을 함께 택합니다. Q2의 기준 — "타이핑 중 반응이 필요 없는 단순 폼은 비제어 허용" — 을 팀 컨벤션으로 정해서, React의 예측 가능성은 지키되 불필요한 세리머니는 줄입니다. 실제로 Vue·Svelte가 양방향 편의를 선택해 성공한 것도 사실이라, "편의가 무조건 틀린 답"은 아닙니다. 팀 규모, 앱 복잡도, 그리고 "값의 출처를 추적 못 해서 생기는 버그"의 과거 이력이 결정 요건입니다.
   한 줄 정리: 소수·단순 앱이면 편의(양방향)도 합리적이지만, 크고 오래 사는 제품이라면 추적 가능성(단방향 명시)이 이긴다 — 다만 단순 폼에서만큼은 비제어로 편의를 되찾는 규칙을 둔다.
